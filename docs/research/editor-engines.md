# Editor engine options

Researched 2026-10-31. Repo facts come from `gh api` on that date. Where something could not be checked it says **unknown**. Bundle sizes are my own esbuild measurements (`--bundle --minify`, then `gzip -9`) of a minimal Markdown setup, not vendor figures.

Hard constraints: no GPL/AGPL/LGPL licence; Sublime/VS Code-style multi-cursor (⌘D next occurrence, add caret above/below, column selection, typing into all carets); Markdown coloring that stays smooth on a 10k-line file.

**WYSIWYG round-trip evidence.** In `prosemirror-markdown` 1.13.9 ([dist](https://unpkg.com/prosemirror-markdown@1.13.9/dist/index.js)):
- Emphasis is always written as `*`.
- Links are always written inline as `[text](url)`, so reference links are lost.
- Hard breaks are written as `\` + newline, so two-space breaks are rewritten.
- Bullets default to `*`.
- The default CommonMark schema has no tables.

None of the WYSIWYG options keeps the source exactly as typed.

## 2. MarkEdit: prior art

- MIT ([repo](https://github.com/MarkEdit-app/MarkEdit)). macOS 26+, about a 4 MB app. "Multi-caret and code folding is built on CodeMirror 6… UI controls remain native… including force-touch word lookup, inline predictions, and Writing Tools" ([README](https://github.com/MarkEdit-app/MarkEdit)).
- Why a web editor: "Implementing features such as multi-caret editing and code folding with TextKit is much harder than with web technologies" ([Why MarkEdit](https://github.com/MarkEdit-app/MarkEdit/wiki/Why-MarkEdit)).
- **How it bridges to native.** Swift↔TS interfaces are code-generated with ts-gyb ([README](https://github.com/MarkEdit-app/MarkEdit)), with typed bridge modules such as `history`, `search`, `selection` and `writingTools` ([CoreEditor/src/bridge/web](https://github.com/MarkEdit-app/MarkEdit/tree/main/CoreEditor/src/bridge/web)). On the native side:
  - A WKWebView subclass overrides `selectAll`, because WebKit's default "only selects the viewport" (CM virtualization) ([EditorWebView.swift](https://github.com/MarkEdit-app/MarkEdit/blob/main/MarkEditMac/Sources/Editor/Views/EditorWebView.swift)).
  - Undo/Redo are routed to the JS bridge rather than `NSUndoManager` ([EditorTextInput.swift](https://github.com/MarkEdit-app/MarkEdit/blob/main/MarkEditMac/Sources/Editor/Views/EditorTextInput.swift)).
  - It has its own native Find panel ([Panels/Find](https://github.com/MarkEdit-app/MarkEdit/tree/main/MarkEditMac/Sources/Panels/Find)).
  - Writing Tools integration reads **private** WritingTools/WebKit classes (`WTWritingToolsViewController`, `WTAffordanceView`) ([AppWritingTools.swift](https://github.com/MarkEdit-app/MarkEdit/blob/main/MarkEditMac/Sources/Main/AppWritingTools.swift)).
- Multi-caret UX it documents: ⌘-drag adds selections, ⌥-drag gives a rectangle, and the context menu has "Select All Occurrences" ([Manual](https://github.com/MarkEdit-app/MarkEdit/wiki/Manual)).

## 3. Native-behavior fidelity: WKWebView + CM6 vs NSTextView

NSTextView gets all of the following for free. The column below covers the web editor.

| Behavior | Web editor in WKWebView | Evidence |
|---|---|---|
| Spell check / grammar | **Preserved, opt-in.** CM6 sets `spellcheck="false"` and `autocorrect="off"` by default, so they must be turned on. MarkEdit says it "supports all native text-checking features", toggled from the Edit menu. | [view src](https://unpkg.com/@codemirror/view@6.43.15/dist/index.js), [Manual](https://github.com/MarkEdit-app/MarkEdit/wiki/Manual) |
| Autocorrect / substitutions | **Preserved, but confusing.** Its settings are app-level (Edit menu), separate from the System Settings toggle. Users report it surprised them. Smart quotes can mix styles. | [#427](https://github.com/MarkEdit-app/MarkEdit/issues/427), [#1746](https://github.com/MarkEdit-app/MarkEdit/issues/1746), [#1691](https://github.com/MarkEdit-app/MarkEdit/issues/1691) |
| Dictation | **unknown.** Neither MarkEdit's docs nor its issues mention it. | n/a |
| Apple Writing Tools | **Preserved, fragile.** WebKit has `writingToolsBehavior` (macOS 15+). CM6 defaults `writingsuggestions="false"`. MarkEdit needs private classes, and its menu-bar entry regressed once. | [Apple](https://developer.apple.com/documentation/webkit/wkwebviewconfiguration/writingtoolsbehavior), [AppWritingTools.swift](https://github.com/MarkEdit-app/MarkEdit/blob/main/MarkEditMac/Sources/Main/AppWritingTools.swift), [#917](https://github.com/MarkEdit-app/MarkEdit/issues/917) |
| Services menu | **Preserved** per MarkEdit ("fully supports system services") | [Why MarkEdit](https://github.com/MarkEdit-app/MarkEdit/wiki/Why-MarkEdit) |
| Emacs keys (⌃A/E/K…) | **Re-implemented in JS.** CM6's `standardKeymap` includes `emacsStyleKeymap` on Mac (Ctrl-a/e/k/d/h/t/o/b/f/n/p/v). Whether a user's `DefaultKeyBinding.dict` is honored: **unknown**. | [commands src](https://unpkg.com/@codemirror/commands@6.11.1/dist/index.js) |
| IME / marked text | **Works, with recurring WebKit-specific composition bugs** (Chinese IME broken after `#`, Pinyin regressions). CM uses EditContext only on Android, so WebKit runs on contenteditable plus a MutationObserver. | [#956](https://github.com/MarkEdit-app/MarkEdit/issues/956), [#358](https://github.com/MarkEdit-app/MarkEdit/issues/358), [view src](https://unpkg.com/@codemirror/view@6.43.15/dist/index.js) |
| VoiceOver | **Degraded/unknown.** CM claims it "works well with screen readers" (`role=textbox`, aria-live). Only the viewport is in the DOM, so off-screen text isn't exposed. Real VoiceOver behavior is unverified. MarkEdit has no VoiceOver issues. | [site](https://codemirror.net/), [guide](https://codemirror.net/docs/guide/) |
| System Find bar | **Lost.** WebKit find can't see off-viewport text, and `isFindInteractionEnabled` is iOS/Catalyst-only. MarkEdit built its own panel on CM search. | [Apple](https://developer.apple.com/documentation/webkit/wkwebview/isfindinteractionenabled), [Panels/Find](https://github.com/MarkEdit-app/MarkEdit/tree/main/MarkEditMac/Sources/Panels/Find) |
| Undo + NSDocument | **Degraded.** Undo lives in CM `history`, routed by hand, not `NSUndoManager`, so dirty-state and close prompts must be bridged. Grouping is time-based (MarkEdit uses 300 ms) and users find it too granular compared with TextEdit. | [EditorTextInput.swift](https://github.com/MarkEdit-app/MarkEdit/blob/main/MarkEditMac/Sources/Editor/Views/EditorTextInput.swift), [#1582](https://github.com/MarkEdit-app/MarkEdit/issues/1582) |
| Typing latency | **unknown.** No measurement found. MarkEdit claims it is "consistently faster than most macOS editors", which is a vendor claim. | [README](https://github.com/MarkEdit-app/MarkEdit) |
| Memory | **Worse.** Each document gets its own WebContent process; a user reports 300–600+ MB per document. The maintainer says a shared `WKProcessPool` "won't actually reduce memory usage" and is deprecated. A separate report has WebContent at 100% CPU. | [#1502](https://github.com/MarkEdit-app/MarkEdit/issues/1502), [#1421](https://github.com/MarkEdit-app/MarkEdit/issues/1421) |

## What this means

- **CodeMirror 6 in a WKWebView is the only candidate that meets all three hard constraints today**: a permissive licence, full Sublime-style multi-cursor, and fast incremental Markdown parsing. It is also the only one with a credible iOS story (Monaco has none). MarkEdit is MIT-licensed proof that a native-feeling macOS 26 app can be built this way, and its source is a reference for the bridge.
- **No native, permissively licensed Swift editor meets the multi-cursor bar.** CodeEditTextView has carets and column selection but no ⌘D, and it is macOS-only and pre-1.0. Runestone has no multi-cursor. NSTextView cannot hold multiple empty carets. Going native means either paying for STTextView or building a multi-caret layer yourself.
- **WYSIWYG options are out.** None of ProseMirror, Tiptap, Milkdown or Lexical supports multi-cursor, and their serializers rewrite the source (emphasis markers, bullets, reference links, hard breaks). That conflicts with "the user's Markdown is the source of truth" and with selection copy re-rendering source ranges.
- **A live-preview feel stays possible later** through CM6 decorations without giving up multi-cursor or exact source. No live-preview library is mature enough to adopt as-is.
- **What a web editor costs:**
  - You own a JS↔Swift bridge for undo/dirty-state, find, select-all and Writing Tools.
  - Memory runs to hundreds of MB per window.
  - IME bugs are tied to WebKit releases.
  - The CLAUDE.md decision to "push bodies via JS" for the preview would mean two web views per document.
- **Not verified here:** dictation and VoiceOver under CM6 + WKWebView. Test them by hand in a prototype before committing.
- **Housekeeping:**
  - CodeMirror and ProseMirror issue trackers have moved to code.haverbeke.berlin.
  - Neon has moved to `slsrepo/Neon`.
  - CLAUDE.md's editor section (STTextView + Neon) is stale whichever way this goes.
